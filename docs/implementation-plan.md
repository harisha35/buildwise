# Buildwise — Implementation Plan

**Companion to:** `README.md` (PRD/SRS v1.0, Aug 1, 2026)
**Purpose:** Translate the PRD/SRS into a concrete engineering plan — architecture, data model, API contract, folder structure, phased delivery schedule, and deployment/testing strategy — so development can start without further design ambiguity.
**Status:** Draft for review. Items still pending stakeholder confirmation in PRD §9 are called out inline as **[ASSUMED]** with the default this plan builds against; flip them later without re-architecting.

---

## 1. Guiding Principles

- **Single-tenant, VM-hosted, boring stack.** No microservices, no Kubernetes, no multi-region — one FastAPI app, one Postgres database, one Next.js app, deployed to the existing Hostinger VM via Docker Compose.
- **Server-enforced authorization.** Every role/permission rule in PRD §3.2 is enforced in the API layer, never trusted from the client.
- **Soft delete for Projects and Workers only** (per NFR), hard delete elsewhere is acceptable but generally avoided in favor of status fields.
- **Money and dates are never computed client-side for anything that gets persisted.** Wage due, invoice status, stock balances — all server-calculated, idempotent, re-derivable from source records.
- **Build vertically, not horizontally.** Each phase ships a usable end-to-end slice (DB → API → UI), not "all backend then all frontend."

## 4. Data Model

Expands PRD §5 into concrete tables with types, constraints, and indexes. All tables get `id BIGSERIAL PRIMARY KEY`, `created_at`, `updated_at` unless noted.

### 4.1 Identity & Access

```sql
users
  id, name, email UNIQUE, password_hash, role ENUM(owner, contractor, supervisor, accountant),
  is_active BOOLEAN DEFAULT true, created_at, updated_at

supervisor_project_assignments
  id, user_id FK(users), project_id FK(projects), UNIQUE(user_id, project_id)

password_reset_tokens
  id, user_id FK(users), token_hash, expires_at, used_at
```

### 4.2 Projects

```sql
project_types        (id, name UNIQUE, is_active)      -- admin-configurable list, FR-1.1
projects
  id, name, client_name, client_contact, location,
  start_date, end_date, project_type_id FK(project_types),
  contract_type ENUM(fixed_price, cost_plus, other),
  budget NUMERIC(14,2) NULL,
  status ENUM(planning, ongoing, on_hold, completed) DEFAULT planning,
  is_deleted BOOLEAN DEFAULT false,
  created_by FK(users), created_at, updated_at
```

### 4.3 Workers

```sql
worker_types
  id, name UNIQUE, default_daily_rate NUMERIC(10,2),
  default_ot_rate NUMERIC(10,2), is_active

workers
  id, name, worker_type_id FK(worker_types), phone, photo_url,
  id_proof_number, id_proof_file_url, address,
  default_daily_rate NUMERIC(10,2) NULL,   -- overrides worker_type default if set
  bank_account, upi_id, joining_date,
  emergency_contact, is_active BOOLEAN DEFAULT true,
  is_deleted BOOLEAN DEFAULT false, created_at, updated_at

project_worker_assignments
  id, worker_id FK(workers), project_id FK(projects),
  custom_rate_override NUMERIC(10,2) NULL,   -- FR-2.5 tier 1
  ot_rate_override NUMERIC(10,2) NULL,
  assigned_at, unassigned_at NULL,
  UNIQUE(worker_id, project_id) WHERE unassigned_at IS NULL
```

**Rate resolution (FR-2.5)** is implemented as a service function, not a DB view:
`resolve_daily_rate(worker_id, project_id)` → checks `project_worker_assignments.custom_rate_override` → `workers.default_daily_rate` → `worker_types.default_daily_rate`. Same pattern for OT rate.

### 4.4 Attendance

```sql
attendance
  id, worker_id FK(workers), project_id FK(projects), date DATE,
  status ENUM(present, absent, half_day),
  ot_hours NUMERIC(4,2) DEFAULT 0,
  applicable_rate NUMERIC(10,2),      -- snapshot of resolved rate at entry time
  ot_rate NUMERIC(10,2),
  recorded_by FK(users), created_at, updated_at,
  UNIQUE(worker_id, project_id, date)

attendance_audit_log
  id, attendance_id FK(attendance), changed_by FK(users),
  changed_at, field_name, old_value, new_value
```

Rates are **snapshotted at entry time** into `attendance` rather than re-resolved later — this is what makes historical reports stable even if wage rates change afterward, and is what `WorkerPayment` sums over.

Same-day double-project attendance (PRD §9.2, open item): **[ASSUMED — warn, don't block]**. The API returns a `409`-style warning payload (`warning: true`, not a hard error) if a worker is already marked present/half-day on another project for the same date; the caller (Supervisor) can confirm and proceed. This defaults to the least destructive behavior and is a one-line service change if the stakeholder later wants a hard block.

### 4.5 Payments & Ledger

```sql
worker_advances
  id, worker_id FK(workers), project_id FK(projects) NULL,
  amount NUMERIC(10,2), date, recorded_by FK(users), note,
  outstanding_amount NUMERIC(10,2)   -- decremented as deductions are applied

worker_payments
  id, worker_id FK(workers), week_start DATE, week_end DATE,
  gross_wage_due NUMERIC(10,2), advance_deducted NUMERIC(10,2) DEFAULT 0,
  net_paid NUMERIC(10,2),
  payment_mode ENUM(cash, bank_transfer, upi),
  proof_reference TEXT NULL, proof_file_url TEXT NULL,   -- FR-4.5: at least one required if not cash
  status ENUM(due, paid) DEFAULT due,
  marked_by FK(users) NULL, paid_at TIMESTAMPTZ NULL,
  created_at, UNIQUE(worker_id, week_start)

worker_payment_project_breakdown
  id, payment_id FK(worker_payments), project_id FK(projects),
  days_present NUMERIC(4,2), ot_hours NUMERIC(4,2), amount NUMERIC(10,2)

worker_advance_deductions
  id, payment_id FK(worker_payments), advance_id FK(worker_advances),
  amount_deducted NUMERIC(10,2)
```

`worker_advance_deductions` is a join table (not modeled explicitly in the PRD's high-level ERD) so a single weekly payment can partially deduct across multiple outstanding advances with full traceability — needed for FR-4.3's ledger accuracy.

### 4.6 Materials & Suppliers

```sql
units_of_measure   (id, code UNIQUE, label)             -- admin-configurable, FR-5.1
suppliers           (id, name, contact_person, phone, address, notes, is_active)
materials
  id, name, category, unit_id FK(units_of_measure),
  default_supplier_id FK(suppliers) NULL, default_unit_price NUMERIC(10,2) NULL

material_stock_movements
  id, material_id FK(materials), project_id FK(projects),
  type ENUM(in, out, wastage),
  quantity NUMERIC(12,2), unit_price NUMERIC(10,2) NULL, total_cost NUMERIC(12,2) NULL,
  supplier_id FK(suppliers) NULL, date, recorded_by FK(users), note

material_expenses
  id, project_id FK(projects), material_id FK(materials) NULL,
  supplier_id FK(suppliers) NULL, amount NUMERIC(12,2), date, recorded_by FK(users)
```

Current stock (FR-5.6) is a **computed value**, not a stored column: `SUM(in) - SUM(out) - SUM(wastage)` per `(material_id, project_id)`, exposed via a service query / materialized view refreshed on read (volumes are low — ~5 projects — so no need for a maintained running-balance column).

### 4.7 Quotations, Milestones, Invoices

```sql
quotations
  id, client_name, project_description, project_ref_id FK(projects) NULL,  -- PRD §9.7: linkable after project creation
  total_amount NUMERIC(14,2), date, validity_date,
  terms TEXT, status ENUM(draft, sent, accepted, rejected) DEFAULT draft,
  created_by FK(users)

quotation_line_items
  id, quotation_id FK(quotations), description, quantity NUMERIC(10,2),
  rate NUMERIC(10,2), amount NUMERIC(12,2), sort_order

milestones
  id, project_id FK(projects), name, description,
  amount NUMERIC(12,2), status ENUM(pending, invoiced, paid) DEFAULT pending

invoices
  id, project_id FK(projects), client_name,
  total_amount NUMERIC(14,2), invoice_date, due_date,
  status ENUM(unpaid, partially_paid, paid, overdue) DEFAULT unpaid,
  created_by FK(users)

invoice_milestones      (id, invoice_id FK(invoices), milestone_id FK(milestones))
invoice_line_items      (id, invoice_id FK(invoices), description, quantity, rate, amount, sort_order)
invoice_payments        (id, invoice_id FK(invoices), amount, date, mode ENUM(cash, bank_transfer, upi), note, recorded_by FK(users))
```

Invoice `status` is recomputed by a service function every time an `invoice_payments` row is inserted/updated/deleted (FR-7.5 logic), plus a lightweight scheduled job flips `unpaid`/`partially_paid` → `overdue` when `due_date` has passed (see §6.4).

### 4.8 Cross-cutting

```sql
audit_log   -- generic append-only log for financial mutations beyond attendance
  id, entity_type, entity_id, action, actor_id FK(users), payload JSONB, created_at
```

Attendance has its own dedicated audit table (FR-3.4); this generic one covers advances, payments, invoice payments, and stock movements for NFR's "audit logging on ... financial transactions" requirement, without over-modeling each case individually.

## 5. Authentication & Authorization

- **JWT access token** (short-lived, 30 min) + **refresh token** (httpOnly cookie, 7 days), rotated on use.
- `passlib` bcrypt for password hashing.
- `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/forgot-password`, `POST /api/v1/auth/reset-password`.
- No self-signup — accounts for Supervisor/Accountant are created by Owner/Contractor via `POST /api/v1/users` (role-gated).
- **Authorization** implemented as two FastAPI dependencies layered on every protected route:
  1. `require_role(*roles)` — coarse role gate per PRD §3.2 matrix.
  2. `require_project_access(project_id)` — for Supervisors, checks `supervisor_project_assignments`; for other roles, passes through. Applied to every project-scoped read/write (attendance, materials, worker payments scoped to their assigned projects, reports).
- The permission matrix (PRD §3.2) is encoded as a single declarative table in `core/permissions.py` (route capability → allowed roles) so it stays auditable in one place instead of scattered `if role ==` checks.

## 6. Core Business Logic (services layer)

### 6.1 Wage Rate Resolution
`services/wages.py::resolve_daily_rate(worker_id, project_id)` and `resolve_ot_rate(...)` implement the 3-tier hierarchy from FR-2.5. Called at attendance-entry time to populate `applicable_rate`/`ot_rate` (snapshotted, per §4.4), with the resolved value returned to the UI as an editable default.

### 6.2 Weekly Payment Calculation (FR-4.1–FR-4.4)
`services/payments.py::compute_weekly_due(worker_id, week_start)`:
1. Pull all `attendance` rows for that worker across **all** projects for the Mon–Sun window.
2. Sum `(present_days × applicable_rate) + (half_days × 0.5 × applicable_rate) + (ot_hours × ot_rate)` — grouped per project for the breakdown table, and totaled for the gross figure.
3. Look up outstanding `worker_advances` for the worker; surface the balance (no auto-deduction — FR-4.2/4.3).
4. Persist a `worker_payments` row with `status=due` (idempotent — re-running for an already-`due`/未-generated week upserts; a `paid` row is never overwritten, only appended-to via new advance-deduction records if needed).
5. On `POST /payments/{id}/mark-paid`, Supervisor supplies `advance_deduction_amount` (0, partial, or full outstanding), `payment_mode`, and proof if required; the service writes `worker_advance_deductions`, decrements `worker_advances.outstanding_amount`, sets `net_paid`, `status=paid`, `paid_at`.

### 6.3 Invoice Status
`services/invoices.py::recompute_status(invoice_id)` — pure function over `SUM(invoice_payments.amount)` vs `total_amount` vs `due_date`, called after every payment mutation and by the nightly overdue-sweep job. Implements FR-7.5 exactly.

### 6.4 Scheduled Jobs (APScheduler, in-process)
- **Weekly payment generation** — every Sunday 23:59 (server timezone = IST **[ASSUMED — currency/locale §9.1 assumed ₹ INR]**), runs `compute_weekly_due` for every active worker with attendance that week.
- **Overdue sweep** — nightly, flips invoices past `due_date` to `overdue` where applicable.
- Both jobs are also exposed as manually-triggerable admin endpoints (`POST /api/v1/admin/jobs/run-weekly-payments`) for recovery/testing without waiting for the schedule.

### 6.5 PDF Generation (Quotations & Invoices)
Jinja2 HTML templates (`pdf/templates/quotation.html`, `invoice.html`) → WeasyPrint → streamed as `application/pdf`. Plain, single professional layout, no GST fields, no logo customization (per FR-6.3/7.6 v1 scope) — logo/letterhead left as an easy template hook for a future phase.

### 6.6 Reports (FR-8.3)
Each report is a dedicated service + endpoint accepting `start_date`/`end_date` (and role-based project scoping applied automatically via `require_project_access`):
- Project Profitability: `Σ(invoice_payments received) − (Σ worker_payment_project_breakdown + Σ material stock-in cost + Σ material_expenses)` per project.
- Attendance Summary, Payment Dues & History, Material Expense, Invoice & Client Payment — straightforward aggregation queries with CSV export **[ASSUMED — PRD §9.3: PDF + CSV, Excel deferred]** alongside PDF for the two document types.

## 8. Frontend Plan

- **Route groups** mirror the PRD §8 screen list exactly (see repo structure §3).
- **Auth guard**: root layout checks session via a server-side call; unauthenticated → redirect to `/login`. Role-based UI hiding is a UX convenience only — the API is the real gate.
- **Mobile-first**: attendance entry (daily grid) and stock/payment entry are the highest-frequency, most likely on-site-on-phone screens — build and test these against a 375px viewport first, then scale up.
- **Attendance Entry** screen: one row per worker, tap-to-cycle status (Present/Absent/Half-day), inline OT hours input, rate shown but editable, bulk-save for the day. This is the single highest-value screen to get right early — treat it as the UX reference for the rest of the app's data-density style.
- **Offline/online**: none required (NFR), but use TanStack Query's retry/error states generously since "always-online" on a construction site is optimistic in practice — clear error toasts, no silent data loss on submit failure.
- **PDF views**: quotation/invoice detail pages have a "Download PDF" button hitting the `/pdf` endpoint directly (browser handles the download), no client-side PDF rendering needed.

## 9. Phased Delivery Plan

Matches PRD §10 phasing, broken into sprints assuming a small team (1–2 backend, 1–2 frontend, shared QA) and ~2-week sprints. Adjust cadence to actual team size; the sequencing/dependencies matter more than the exact dates.

### Phase 0 — Foundations (Sprint 0, ~1 week)
- Repo scaffolding (backend + frontend + docker-compose), CI pipeline, linting/formatting (ruff/black, eslint/prettier), Alembic baseline migration.
- Deployment skeleton on Hostinger VM (Docker Compose + Nginx + Certbot) reachable at a staging URL, even before real features exist — de-risks deployment early.
- Decide and lock the PRD §9 open items with the stakeholder (see §11 below) before Phase 1 starts, since several (currency, double-attendance behavior, notification channel) touch schema/UX choices made in Phase 1.

### Phase 1 — Core (Sprints 1–4, ~6–8 weeks)
**Goal: a Supervisor can mark attendance and get paid, an Owner can see it.**
1. Auth (login, JWT, forgot-password), User management, role/permission scaffolding.
2. Projects CRUD + archive, Project Types config.
3. Workers CRUD + Worker Types config, project-worker assignment, rate resolution.
4. Attendance entry (daily grid), edit/backdate with audit log, same-project-day duplicate warning.
5. Weekly payment computation job + due screen + mark-as-paid flow with proof upload.
6. Advances (record, view outstanding).
7. Worker Ledger view.
8. Dashboard v1 (attendance summary, payments due — the two data sources that exist so far).
- **Exit criteria:** end-to-end demo — create project, add workers, mark a week of attendance across two projects for a shared worker, generate Sunday payment, mark paid with UPI proof, see ledger update.

### Phase 2 — Materials & Suppliers (Sprints 5–6, ~3–4 weeks)
1. Material/Supplier masters, Units config.
2. Stock In/Out/Wastage entry, current-stock view per project.
3. Direct material expense entry.
4. Material Expense Report.
5. Dashboard: material spend summary added.
- **Exit criteria:** stock and spend numbers for a project are traceable and match manual reconciliation.

### Phase 3 — Quotations, Milestones, Invoices (Sprints 7–9, ~5–6 weeks)
1. Quotation CRUD + line items + PDF export.
2. Milestone management per project.
3. Invoice CRUD (against milestones) + line items + PDF export.
4. Invoice payments (partial support) + auto status transitions + overdue sweep job.
5. Reports: Invoice & Client Payment Report.
6. Project Profitability report (needs labour + material + invoice data — natural fit once all three exist).
- **Exit criteria:** full quotation-to-paid-invoice flow demoable with PDFs matching the "clean, no-GST" spec.

### Phase 4 — Dashboards, Reports Polish, Hardening (Sprints 10–11, ~3–4 weeks)
- Fill remaining report gaps (Attendance Summary, Payment Dues & History standalone views) if not already complete incrementally.
- CSV export across reports **[per §9.3 assumption]**.
- Full role-based dashboard pass for all four roles.
- Security review: rate limiting on auth endpoints, dependency audit, backup verification (restore drill on the VM), HTTPS/cert renewal check.
- Load/sanity check against target scale (~5 projects, 50 workers, 50 suppliers, 10 users) — not a formal load test, just confirm no N+1 query issues at this trivial scale.
- UAT with the actual contractor/owner stakeholder using real (or shadow) data for at least one full weekly payment cycle before go-live.

### Post-v1 candidates (explicitly out of scope, tracked for backlog)
Matches PRD §2.2 — native apps, offline sync, GPS/biometric attendance, GST support, quotation→invoice automation, supplier payable ledger, low-stock alerts, i18n, multi-tenant SaaS, statutory payroll deductions, SMS/WhatsApp notifications.

## 10. Testing Strategy

| Level | Tooling | Coverage focus |
|---|---|---|
| Unit | pytest | wage resolution hierarchy, weekly payment calc, invoice status transitions, stock balance math — these are the modules where a silent bug directly costs someone money |
| Integration | pytest + httpx against a real test Postgres | full API request/response per endpoint, including role-based 403s |
| E2E | Playwright | login → mark attendance → generate/pay weekly payment; create quotation → invoice → record payment → PDF download; each run against a seeded staging-like DB |
| Manual/UAT | stakeholder walkthrough | Phase exit criteria above, plus a real payment cycle before go-live |

CI runs unit + integration on every PR; E2E runs on merge to the main development branch and before each deploy.

## 12. Deployment

- **Environments:** `staging` and `production`, both on the same Hostinger VM initially (separate Docker Compose projects/ports), single Postgres instance with separate databases.
- **docker-compose.prod.yml:** `backend` (FastAPI + Uvicorn/Gunicorn workers), `frontend` (Next.js, standalone build), `db` (Postgres, named volume), `nginx` (reverse proxy + TLS termination), `certbot` (renewal sidecar).
- **Migrations:** run via `alembic upgrade head` as a release step (Compose `command` override or a one-shot job) before the backend container restarts.
- **Backups:** nightly `pg_dump` to a rotated local directory (and ideally off-VM, e.g. rsynced to object storage) per NFR's "nightly database backups recommended" — treat this as required, not optional, given it's the only copy of financial ledger data.
- **Secrets:** `.env` files outside version control, `SECRET_KEY`/JWT signing key, DB credentials, SMTP (if/when needed) — managed via the VM's environment, not committed.
- **Monitoring:** minimal for v1 — Uvicorn/Nginx access logs + Postgres logs retained locally; an uptime check (e.g. a free external ping monitor) on the public URL is a cheap addition worth doing from day one.
